# 网页版干活（v2）

把**大批量生成**派给免费的 DeepSeek 网页版；昂贵的 API 只做拆解和验收。

---

## 设计取舍（一句话）

naive 做法（把规格写进提示词）实测**反而贵 24%** —— 规格会常驻上下文，
之后每一步都要重读。本技能的做法是：**规格从磁盘读、产物写回磁盘，
两者都不进入调用方上下文**。

详细数据见 `docs/BENCHMARK.md`。

## 什么时候用（硬门槛）

**产出量 ≥ 说明量的 5 倍** 才值得派活。

✅ 适合
- 一次生成 **2000+ 行**代码 / 大量同构样板
- 一次生成 **5 个以上文件**
- 批量测试用例、批量文档
- 有**自动验收手段**（pytest / 编译 / lint）

❌ 不适合
- 500~700 行以内的小项目（实测不划算）
- 需要精确逻辑、边界处理（返工比省的多）
- 要 1 分钟内出结果
- 没有自动验收（你就得读全文，等于白干）

## 标准用法（一条命令搞定）

```bash
python skill/ask_web.py \
  --spec C:\path\spec.md \
  --task "实现 models.py 和 test_models.py" \
  --out-dir C:\path\out \
  --pytest
```

脚本会：
1. 从磁盘读 `--spec`（**内容不进你的上下文**）
2. 拼上 `--task`（20~50 字）+ 输出协议
3. 调桥接 → 网页版生成
4. 按 `<<<FILE:xxx>>>` 标记拆分，写到 `--out-dir`
5. 在 out-dir 跑 `pytest`（只取最后一行摘要）
6. **只打印一行结果**，例如：

```
[1/3] 2 个文件, 205 行, 47s → models.py(120行), test_models.py(85行)
[pytest] 12 passed in 0.31s
```

**你看到的就这么多** —— 规格和产物都没进上下文。

### 批量派活

```bash
# tasks.txt 每行一个任务
python ask_web.py --spec spec.md --task-file tasks.txt --out-dir out --pytest
```

```
[1/3] 2 个文件, 205 行, 47s → ...
[pytest] 12 passed
[2/3] 2 个文件, 180 行, 39s → ...
[pytest] 18 passed
[3/3] 3 个文件, 260 行, 58s → ...
[pytest] 8 passed
```

### pytest 工作目录（自动探测）

模型输出的路径可能带项目根（如 `taskman/taskman/models.py`），
直接在最外层跑 pytest 会因为 import 失败而报错。

脚本会自动推断：

| 产物结构 | 探测结果 |
|---|---|
| 全部在 `taskman/` 下 | `<out-dir>/taskman` |
| 文件直接在根下 | `<out-dir>` |
| 分散在多个顶层目录 | `<out-dir>` |

想手动指定就用 `--pytest-cwd <目录>`。

实际输出会多一行，方便确认：
```
[1/4] 2 个文件, 306 行, 141s → ...
[pytest cwd] taskman
[pytest] 117 passed in 0.54s
```

## 输出上限与深度思考

### 单轮输出上限（重要）

网页版**单次回复有长度上限**。实测数据（2026-11-01）：

| 测试 | 结果 |
|---|---|
| 要求输出 20,000 行数字 | 在 **10,814 行 / 53,777 字符** 处被截断，`finish_reason=length` ✅ |
| 700 个函数（704 行 / 31,248 字符） | 正常完成，未截断 |
| 300 个函数（335 行 / 17,596 字符） | 正常完成，未截断 |

**结论：上限约 54,000 字符。**
折合成代码：
- 每行 ~35 字符 → **约 1,500 行**
- 带完整测试的文件对 → **约 1,200 行**

**安全阈值：单次控制在 1,000 行以内。**

超过就会**静默截断** —— 文件写到一半就结束。脚本会检测到并在输出里警告：

```
[2/4] 2 个文件, 411 行, 25s → store.py(169行), test_store.py(242行)
⚠ 回复被网页版**截断**（达到单轮输出上限）
   → 文件可能不完整，请把这个任务拆小后重派
```

**对策**：

| 情况 | 做法 |
|---|---|
| 单个文件 > 600 行 | 拆成两个任务分别输出 |
| 一次派多个文件 | 每次 **不超过 2~3 个文件**，总行数控制在 1,000 行内 |
| 已经截断 | 把那个任务拆小重派，**不要**手工补（补的内容会进上下文） |

### 模型会"自我压缩"（实测发现）

要求生成大量重复内容时，模型**不一定会老实展开** —— 它会自动抽象成循环/工厂函数。

实测：

| 要求 | 实际产出 |
|---|---|
| 2000 个函数 func_0001~func_2000 | **14 行**（用 `globals()` + 循环动态生成） |
| 700 个函数 | 704 行（老实展开了） |

**这是好事还是坏事，取决于你要什么：**

| 你要的 | 建议 |
|---|---|
| 可维护的代码（DRY） | ✅ 让它压缩，别管 |
| **必须逐个展开**（每个有差异、要能单独 grep、要给非技术人员看） | ❌ **必须明确禁止压缩** |
| 生成大量**不可压缩**的内容（数据、清单、文档） | ✅ 天然会展开，注意上限 |

### 强制展开的写法

在 `--task` 或提示词里加：

```
禁止使用循环、globals()、eval、工厂函数或任何代码生成技巧。
必须逐个完整写出每一个函数/条目，即使内容高度重复。
每个函数之间必须有实际差异（如不同的 docstring 或默认值）。
```

**反例**（模型会偷懒）：
```
生成 2000 个函数，每个返回自己编号的平方
```

**正例**（能拿到真展开）：
```
生成 500 个函数 func_0001~func_0500。
禁止使用循环或代码生成，必须逐个完整写出。
每个函数的 docstring 要写明它处理的业务场景（各不相同），返回值是编号的平方。
```

⚠️ 展开后行数会暴涨，注意配合上面的**输出上限**（约 1,500 行）拆分任务。

### 深度思考（THINK）

网页版的"深度思考"开关会影响：

| | 开启 | 关闭 |
|---|---|---|
| 延迟 | **60~180 秒** | 15~30 秒 |
| 质量 | 复杂逻辑更稳 | 简单样板足够 |
| token | 消耗思考 token（但**免费**） | 无 |

**桥接不控制这个开关**，由网页设置决定。建议：

- **批量生成样板代码** → 关掉思考（快 5 倍）
- **复杂算法/难逻辑** → 打开（质量优先）

脚本解析会自动**丢弃思考内容**，只取最终答案，所以你不用担心中间过程混进结果。

## 关键原则

### 1. 规格必须在磁盘上，不要写进提示词

```bash
# ❌ 错：把 400 行规格写进提示词
write task.md  （400 行规格 + 要求）

# ✅ 对：规格早已在磁盘，只用 20 字指路
ask_web.py --spec spec.md --task "实现 models.py"
```

**规格文件本身**该由用户提供或复用现成的（如 `project_spec.md`），
不要每次派活都重写一份。

### 2. `--task` 越短越好

好的 task（20~50 字）：
```
实现 models.py 和 test_models.py，注意 Task.validate 的边界
```

坏的 task（200+ 字）：
```
请你实现 models.py，里面要有一个 Task 数据类，字段有 id、title、
status、priority、tags、created、done_at，validate 方法要检查……
```
→ 这些细节应该在 **spec 文件**里，不在 task 里。

### 3. 验收用工具，不要用眼睛

```bash
--pytest            # 脚本内跑，只回摘要
```

需要更多检查时，用一行命令：
```bash
python -m py_compile out/*.py && echo OK
```
**不要** `read` 生成的文件来"看看对不对" —— 那等于把产物拉进上下文，白干。

### 4. 出问题只读局部

```bash
# ✅ 只读报错那一小段
python -m pytest out -q --tb=line 2>&1 | tail -3
```

## 常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| `未解析到文件标记` | 模型没按协议输出 | 在 task 里重申"只输出 `<<<FILE:...>>>` 格式" |
| `返回空内容` | 浏览器没登录 / 被限流 | 去浏览器登录一次；隔几分钟再试 |
| pytest 全红 | 提示词太笼统 | 拆小任务，或在 task 里点名"先写 models 再写 store" |
| `ImportError: No module named xxx` | pytest 跑错目录 | 看输出里的 `[pytest cwd]`；必要时 `--pytest-cwd <项目根>` |
| 某个文件缺失 | 拆分后没生成 | 单独补派一个 task |
| 文件明显写一半 | **达到输出上限被截断** | 把任务拆小，每个文件 <600 行 |
| 等待时间超过 2 分钟 | 网页开了深度思考 | 去网页关掉，或用小任务 |
| 要 2000 个函数只给了 14 行 | 模型自我压缩 | 提示词里禁止循环/代码生成，要求逐个展开 |
| 超时 | 任务太大 | 拆小；或 `--timeout 1200` |

## 判断要不要派活的算法

```
派活收益 = (你原本要输出的 token × 1.5)
         − (派活新增的输入 token × 1 + 新增缓存读取 × 0.1)
         − (等待时间的隐性成本)
```

**经验阈值**：

| 产出规模 | 建议 |
|---|---|
| < 500 行 | ❌ 自己写 |
| 500~1500 行 | ⚠️ 看情况，收益不明显 |
| **> 2000 行 / > 5 个文件** | ✅ **派活**，收益明显 |
| 批量同构（20 个相似文件） | ✅✅ 强烈推荐 |

## 与直接改模型的区别

**不要把 DSH 的模型切换成网页版**。它扛不住完整工具目录（40 个工具的 schema），
会退化、重复、乱输出。

正确姿势就是本 skill：**DSH 保持 API，只把"生成"这一步外包出去**。
